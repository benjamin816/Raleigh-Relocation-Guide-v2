# Living in Raleigh chat booking service (TEST)

This is a separate Google Apps Script web app. Test version 3 was deployed on October 27, 2026 at `https://script.google.com/macros/s/AKfycbysLAettKRWslMW8YgG3BxftA2eBL_gsZFdK70bN7B3xu-aG_stqdNqg3jYBB5aqoMa2g/exec`. The static site cannot read or write a private Google Calendar directly. If the bridge fails, chat offers to pass details to the team or gives the team phone number.

The service checks the Living in Raleigh Team calendar and both hosts' source calendars, uses 60-minute Eastern Time slots, and rechecks the slot under a lock. Version 3 reads each conflict calendar once for the search window, then evaluates slots in memory. It reads the existing `Appointment Assignments` ledger, favors openings for the host due next, and reserves a named Benjamin or Ricardo request only when that person is available. By default it offers an afternoon and an evening opening; a visitor can request mornings, a particular day, weekends, or a named host. On booking it creates one event on the team calendar, invites the visitor and assigned host, writes the assignment ledger, and writes the lead to `Chat Appointments`. The existing 10-minute round-robin job recognizes the ledger row and sends the team notification. The visitor does not need an emailed code.

The owner then authorized deployment for testing. The local Test site has `chatVideoBookingEnabled` and `chatRoundRobinBookingEnabled` enabled. Do not promote the Test changes to main until the booking and pre-call email path are verified. An event created directly is not a Google Appointment Schedule booking. The October 27 local revision adds the pre-call email directly to this booking service, using the current email's optional form and relocation guide. This revision still needs a new Apps Script deployment and a live booking test; the currently deployed version 3 does not send that email.

The public service limits completed bookings to 20 per day globally and two per email per day, checks availability again before creating the event, and reuses a six-hour receipt for duplicate requests. These limits reduce accidental repeats and volume abuse, but they cannot prove that the visitor owns the email address or stop someone from entering false contact details. Monitor the calendar and raise or lower the daily cap based on real traffic. If abuse appears, add a stronger server-side challenge or return to the native Google booking page.

## Admin consultation page

`/admin/consult/` uses the same team-owned calendar service. The page is excluded from indexing and uses the same simple client-side passcode convention as the temporary Ricardo preview page. The passcode is only a convenience gate, not a security boundary: anyone inspecting the page source could find it. This page does not expose private lead data; the underlying booking endpoint and availability were already public through the Test chat.

The Benjamin/Ricardo choice is passed to the already deployed server-side slot filter. Booking rechecks the selected person's calendars under the existing lock and passes `preferredHost` to the assignment logic. The resulting event invites that person and the visitor, records the host in `Appointment Assignments`, and adds the contact to `Chat Appointments`. The admin form does not use the public Google appointment schedule iframe. Verify one Benjamin-only and one Ricardo-only availability case and one booking with each host; do not claim assignment is proven by page display alone.
