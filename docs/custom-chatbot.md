# Custom Raleigh chat (TEST branch)

The website chat is a static, dependency-free, rule-based guide. It does not use Tawk, an LLM, a paid API, or an external chatbot platform. Its scripts, keywords, questions, FAQ answers, resource URLs, and booking wording live in `assets/js/raleigh-chat-config.js`. The runtime is `assets/js/raleigh-chat.js`, intent and moderation rules are in `assets/js/raleigh-chat-engine.js`, and styles are in `assets/css/raleigh-chat.css`. Visitors type replies naturally; there are no quick-reply buttons.

The standalone flow editor has been retired. Conversation wording, starter message, branches, keywords, and resource links remain in `assets/js/raleigh-chat-config.js`; update them through the TEST branch chat workflow. Living buyers, sellers, and relocation leads can book a call inside the chat; investors are directed to `/invest/` to book and `/invest/resources/` for articles. The public website cannot write to the configuration file.

The suggested MIT Chatbot Flow Builder Starter Kit was evaluated. It is a separate React/React Flow/Vite editor shell, while this site and its widget are plain static HTML and JavaScript. The chatbot keeps one deployable configuration file and has no flow editor runtime dependency.

For local review of both the site and the calculator, run `python scripts/serve-test-site.py --port 8777` from this repository. It serves this site plus the already-built `dist/` from the sibling One-Stop-Rental-App at `/calculator/`. The helper binds only to `127.0.0.1` and does not change public hosting.

The widget runs on pages that load `assets/js/script.js`, plus the standalone `/invest/` page. It is hidden on `/consult/` and `/2026/` to avoid competing with those forms. The generated fictional avatar is `assets/images/chat/raleigh-guide-avatar.png`. It should not be represented as a real team member or live agent. A bounded chat transcript and topic answers are saved for the configurable duration (currently 365 days) in that browser's local storage, so a repeat visitor on the same browser can resume without another starter message. Opening saved chat scrolls to its newest message. The bot can recap prior answers when the visitor revisits a topic or types `what do you remember`; `start over` restarts the current topic. `forget` erases this browser's saved chat. A **Reset test conversation** button does the same on localhost only and is absent from the public site. Email and phone patterns are redacted from saved chat history; the contact handoff's name, email, phone, and question are never stored in that browser history. This is not cross-device identity or a secure server-side conversation archive. Shared-device users can see the saved chat until they use `forget` or clear site data. Only an explicit contact request is transmitted.

Direct chat booking has a separate Google Calendar bridge under `scripts/google-apps-script/chat-booking/`. Version 3 of the Test bridge was deployed on October 27, 2026, after owner authorization. It reads the existing `Appointment Assignments` round-robin ledger before suggesting slots. It favors the host due next, defaults to one afternoon and one evening option, and accepts a requested weekday, weekend, morning/afternoon/evening, or Benjamin/Ricardo. A named host request must pass that person's availability check. At booking it rechecks the time, assigns and invites the host, records the same round-robin ledger row, and writes the lead to `Chat Appointments`; a video call requests a Google Meet link. Both `chatVideoBookingEnabled` and `chatRoundRobinBookingEnabled` are enabled on the local Test site. The separate pre-call email path is still unverified. The flow has no emailed verification code. A public booking endpoint cannot prove the visitor owns the email address. Daily booking limits and duplicate-request protection reduce abuse but do not eliminate that risk. The bridge uses a credentialless iframe to avoid Google account-routing failures; verify it in the browser before promoting direct booking to main.

FAQ replies answer a question and then return to the current qualification question. Buyer and relocation paths branch on local versus out of state, then renter versus owner. An owner who needs to sell moves into the combined selling-and-buying path. Initial Ohio and New York location details are acknowledged without asking for location again. Unknown questions offer a relevant resource and a call, while investing questions lead to the investor call page. Incidental profanity is allowed. A first spam, abusive, or discriminatory message gets a warning; a second ends the chat. Direct threats or hate slurs end it immediately. Moderation reasons are recorded in local storage and sent to the existing analytics tracker when present. The repeat-offender restriction is same-browser only and can be cleared with browser data; reliable cross-device enforcement needs a server-side identity and moderation service. `tests/chat-conversation-matrix.test.cjs` covers 106 text, interruption, moderation, and branch cases; longer browser conversations were also exercised. No booking was created during those conversation tests.

## Lead storage

The conversational contact handoff asks for name, email, phone, question, and explicit contact consent one message at a time. After consent, it sends those details, interest, and conversation context over HTTPS to the site's **existing** Google Apps Script website lead receiver. The receiver appends the canonical row to the private `Master Leads` spreadsheet's `Website Direct Leads` tab. Submissions are identified by `source_key=website_rule_chat`. The new **Website Chat Leads** tab in that same spreadsheet is a filtered view of those rows; it updates without another Apps Script deployment. The tab is not a second independent database.

The endpoint is cross-origin and used in `no-cors` mode, as with the existing website forms. The browser can detect a network failure but cannot read the Apps Script response or prove that a particular row was stored. The UI says “submitted for processing,” not “received by our team.” Each retry reuses one submission ID so the receiver can deduplicate it. The existing receiver sends admin email only when a phone number is present, so the contact conversation requires phone.

The Test composer includes voice typing through the browser's speech recognition API. The browser may ask the visitor for microphone access. Recognition stays active across multiple phrases when the browser supports continuous speech recognition; recognized and interim speech fills the message field for review and does not send itself. The message field wraps and grows to 142 pixels, then scrolls inside the field for longer messages. Enter sends; Shift+Enter adds a line. Sending, minimizing, or resetting the chat stops recognition. The file button accepts one JPG, PNG, WebP, or PDF up to 4 MB, only for the Living in Raleigh contact handoff. The updated receiver validates the file signature, leaves the large encoded file out of the lead sheet, records its name there, and attaches it to the team's lead email. The Test receiver was deployed on October 27, 2026; one synthetic PNG submission returned success and the team email contained the attachment. Investor attachments need a separate investor intake path.

An end-to-end synthetic POST on October 23, 2026 returned `ok:true`, appeared on the new tab with the expected fields, and was then removed from the source sheet. This validates the route and tab formula, not per-visitor acknowledgement. Before promoting to main, add server-side input validation, formula-injection protection, rate limiting/spam controls, and a readable acknowledgement route if confirmed delivery is required. Investor conversations never submit to this Living in Raleigh receiver. The chat directs investor questions to the separate calculator message form and investing calls to `/invest/`. Direct investor lead capture inside the chat still requires a verified investor receiver with a readable success acknowledgement and the separate Investor Master Lead Sheet.

## Smoke test

1. Open the local TEST site. Confirm the chatbot starts with the configured message and routes through the buying, selling, relocating, and investing paths.
2. Open the chat on desktop and mobile. Confirm the gold launcher stays visible, hover/focus shadow, tall narrow panel, mobile layout, message timestamps, and Escape/close focus behavior.
3. Type buying, selling, selling-and-buying, relocating, and investing requests; follow the free-text qualification questions and check Living in-chat booking and investor `/invest/` links.
4. Submit a synthetic contact request through a network-intercepted browser test. Verify `source_key=website_rule_chat`, interest, question/context, and that no mail client opens.
5. For a real end-to-end storage test, use a clearly marked synthetic submission with no phone so it sends no admin alert, verify it on the Sheet's chat tab, then remove only that test row.
6. Confirm no request to `embed.tawk.to` appears in network activity.
7. Reload after a completed or partially answered chat. Confirm timestamps and prior messages return, a completed topic recalls previous answers rather than asking them again, and contact details do not appear in local storage. Type `forget`, reload, and confirm the fresh starter returns.
